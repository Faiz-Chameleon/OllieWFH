## 3. Production incident — `api.theollie.app` DNS missing — 🔴 OPEN (external)

**Symptom:** iOS simulator login showed "Please check your internet connection and try again." for `jack@yopmail.com`.

**Root cause:** `api.theollie.app` has **no DNS record — `NXDOMAIN`**. Not the app, not the user's connection.

Evidence gathered (all **read-only probes from the local machine**; nothing on the server was changed):

| Check | Result |
|---|---|
| `dig api.theollie.app` | `status: NXDOMAIN` (no A, no CNAME) |
| via `8.8.8.8` | NXDOMAIN — not a local cache/ISP issue |
| `theollie.app` (apex) | resolves → `185.181.255.109`, HTTP 200 |
| `google.com` (control) | resolves normally |
| Nameservers | `ns1`–`ns4.mysecurecloudhost.com`, answering authoritatively |
| `POST https://theollie.app/api/v1/user/auth/userLogin` | **404** — apex does *not* serve the API |
| Old IPs `3.96.147.42`, `3.96.202.108`, `3.96.158.243` | all **unreachable** — no fallback host |

**Backend is healthy.** On the VPS `187.77.111.201` (srv1526101, Ubuntu 24.04.4), `pm2 ls` shows `ollie-backend` **online, 12 D uptime, 2 restarts**; ports 80/443 open. Simulating the restored record proves the whole stack works:

```
curl --resolve api.theollie.app:443:187.77.111.201 \
     https://api.theollie.app/api/v1/user/auth/userLogin \
     -X POST -H 'Content-Type: application/json' -d '{}'

→ {"success":false,"message":"userEmail is required"}   [HTTP 400]
→ subject: CN=api.theollie.app | issuer: Let's Encrypt | SSL certificate verify ok
```

That 400 is the real backend validating the empty body. The same request **without** `Host: api.theollie.app` returns `404 not_found` (nginx default vhost) — confirming the API is bound to that specific virtual host.

**The fix is one DNS record**, in the mysecurecloudhost DNS zone:

```
api.theollie.app.    A    187.77.111.201
```

**⚠️ Deadline:** the Let's Encrypt cert for `api.theollie.app` expires **2026-09-21 (13 days out)**. Certbot's HTTP-01 challenge requires the hostname to resolve publicly, so **auto-renewal is already failing silently**. Restoring the record before the 21st fixes both; after that date it becomes a resolve-but-expired-cert outage. Verify with `certbot renew --dry-run` once DNS propagates.

**Status:** message drafted and handed to the user to forward to the backend team. **No app-side change needed** — `ApiUrls.baseUrl` (`lib/app_urls.dart:7`) is correctly `https://api.theollie.app/api/v1`.

**Why the app blamed the user's Wi-Fi:** `lib/api_service.dart:33-36` maps any `SocketException` to "Please check your internet connection and try again." Dart throws `SocketException` for a failed **DNS lookup** too, so the app cannot distinguish "device offline" from "hostname does not exist".
